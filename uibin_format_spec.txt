================================================================================
  .uibin File Format Specification  (Version 4)
================================================================================

A .uibin file is a self-contained, binary-packed UI scene produced by
UIMaker2's "Bake" command. It bundles the entire UI element hierarchy together
with every referenced texture/font asset into one file that a game engine can
load at runtime with zero external file dependencies.

This document is both the byte-level reference AND a usage guide: each section
gives the exact layout, explains what the part is for, and tells you how to
consume it. If you are writing an engine-side loader, you can implement it
top-to-bottom from this file alone.


--------------------------------------------------------------------------------
  1. Design goals (why the format looks like this)
--------------------------------------------------------------------------------

  * Opaque and fixed-layout. It is deliberately NOT text/JSON-shaped and not
    meant to be eyeballed. Every value is found by an explicit offset in the
    header or by a length prefix - never by scanning for delimiters. This is
    what makes loading a few memcpy-style reads instead of a parse.

  * Little-endian everywhere. All multi-byte scalars are little-endian, which
    is native on the target platforms, so reading an integer is a direct load
    with no byte-swapping. There is no padding or alignment between fields.

  * Strings interned once. Every repeated string (component type names,
    property names, element names, asset identity) is stored a single time in
    a string table and referenced by a 4-byte id. The tree itself contains no
    text, only ids.

  * Engine-facing asset identity is first-class. Each asset carries an
    abstract (domain, registryValue) pair the engine can resolve through its
    own asset registry, AND the raw baked bytes as a fallback. The editor's
    authoring path (the relative imagePath/fontPath/iconPath) is intentionally
    NOT in the file - it is a tooling concept with no runtime meaning.

  * Forward-skippable. Components are length-prefixed so an older loader can
    walk past a component type or field tag it does not understand instead of
    failing.

  * Eyeball-opaque body. Every byte after the 32-byte header is run through a
    deterministic XOR stream (see section 2a) so a hex dump shows noise -
    no component names, no PNG/TTF magic bytes, no element names. The header
    stays in the clear so a loader can locate sections without demasking.
    This is cosmetic obfuscation, not cryptography: anyone with the spec or
    the source can decode the file. It exists only to keep baked content
    from being casually readable.


--------------------------------------------------------------------------------
  2. How a runtime loads a .uibin (the whole procedure)
--------------------------------------------------------------------------------

  1. Read the 32-byte header. Verify magic == "UIB4" and version == 4. Reject
     otherwise. Keep the four section offsets and three counts.
  2. Demask everything from offset 32 to EOF in place (or into a working
     buffer) using the XOR stream described in section 2a. The header is
     already in the clear; do NOT demask the first 32 bytes. From this
     point on, treat the demasked bytes as the file you are parsing.
  3. Seek to stringTableOffset. Read [stringCount] entries into an array
     indexed by id (id 0 will be ""). This array is your decode dictionary.
  4. Seek to assetTableOffset. Read [assetCount] records into an array indexed
     by asset index. Resolve string ids to get each asset's domain/registry.
     Either register the embedded bytes with your texture/font system now, or
     keep them lazily and resolve on first use.
  5. Seek to treeOffset. Decode exactly one Element (recursive, pre-order).
     For each component, instantiate it by its type-name string, then apply
     each field to the instance (see section 7).
  6. The decoded Element tree is your live UI hierarchy.

Sections never overlap and always appear in this order, but you should always
trust the header offsets rather than assume adjacency.


--------------------------------------------------------------------------------
  2a. The XOR mask  (applied to all bytes after the header)
--------------------------------------------------------------------------------

  Every byte in the file from offset 32 onwards is XORed with a stream
  produced by this linear-congruential generator. Writer and reader run the
  identical routine; XOR is self-inverse so one call encodes and the other
  decodes.

      uint32 s = 0x5BC8A93D                       // seed (constant)
      for i in 0 .. n-1:
          s = (s * 1103515245 + 12345) mod 2^32   // glibc rand() LCG
          data[i] ^= uint8(s >> 16)               // high byte of state

  The seed is fixed; the stream depends only on byte position within the
  masked region (offset 0 of the stream = file offset 32). String table,
  asset table, and element tree are masked as one contiguous run - do NOT
  reset the generator between sections.

  Why this exists. Without the mask, baked files leak readable property
  names ("position", "imagePath"), component names ("Transform", "Button"),
  element names from the editor, and recognisable file signatures inside
  the asset table (e.g. PNG's "\x89PNG", TTF version bytes). With the mask
  applied, every byte after the header is indistinguishable from random
  noise in a hex dump.

  What this is NOT. It is not encryption. The seed and algorithm are right
  here; anyone with this document or the source can reverse the mask. The
  goal is "not casually eyeballable", not secrecy.


--------------------------------------------------------------------------------
  3. Header  (fixed 32 bytes, at offset 0)
--------------------------------------------------------------------------------

  Offset  Size  Type    Description
  ------  ----  ------  ------------------------------------------------------
  0       4     char[4] Magic bytes: ASCII "UIB4"
  4       2     u16     Format version (currently 4)
  6       2     u16     Flags (currently 0; all bits reserved, must be 0)
  8       4     u32     String table offset  (always 32)
  12      4     u32     String count
  16      4     u32     Asset table offset
  20      4     u32     Asset count
  24      4     u32     Element tree offset
  28      4     u32     Total file size in bytes

  What it's for: a self-describing directory of the file. Because every
  section's start is here, a loader needs no preliminary scan. The header
  is also the only part of the file that is NOT XOR-masked (see section
  2a), so these 32 bytes are recoverable straight from disk.

  How to use it: validate magic+version first, BEFORE demasking. Earlier
  formats (v1 JSON blob, v2 binary layout, v3 cleartext binary) must be
  rejected - v4 is not backward compatible and a loader must not attempt a
  best-effort parse of a mismatched version. Treat the offsets as
  authoritative. Use "Total file size" as a sanity check: if it does not
  equal the actual file length the file is truncated/corrupt.


--------------------------------------------------------------------------------
  4. String table  (at stringTableOffset)
--------------------------------------------------------------------------------

  Repeated [String count] times, contiguously:

  Size    Type    Description
  ------  ------  --------------------------------------------------------------
  4       u32     Byte length of the UTF-8 string  [len]
  len     u8[len] UTF-8 bytes, no null terminator

  What it's for: deduplication. The same property name ("imagePath") or
  component type ("Image") occurs hundreds of times in a scene; storing it
  once and referencing a 4-byte id keeps files small and decoding fast.

  How to use it: read the whole table into an array once, BEFORE touching the
  asset table or tree, because both reference strings by id. Ids are assigned
  in order of first appearance starting at 0, and id 0 is, by contract, always
  the empty string - so you can treat a 0 id as "" without a lookup.


--------------------------------------------------------------------------------
  5. Asset table  (at assetTableOffset)
--------------------------------------------------------------------------------

  Repeated [Asset count] times, contiguously:

  Size      Type      Description
  ------    ------    ----------------------------------------------------------
  4         u32       Domain string id           (engine-facing asset domain)
  4         u32       Registry value string id   (engine-facing registry key)
  4         u32       Raw asset data length      [dataLen]
  dataLen   u8        Raw baked file bytes (PNG/JPG/TTF/OTF/...), no terminator

  What it's for: this is the heart of the new asset model. An asset is NOT a
  file path. It is an abstract identity - (domain, registryValue) - that means
  something to your engine's asset registry, plus a self-contained copy of the
  bytes so the file still works even if the registry has no entry.

    - domain        : a namespace/category the engine understands, e.g.
                      "ui", "items", "fonts". Opaque to the editor.
    - registryValue : the key within that domain, e.g. "hero_portrait".
                      Opaque to the editor.
    - bytes         : the actual encoded image/font, decoded with your normal
                      image/font loader.

  Both are always present. dataLen may be 0 (the source file was missing at
  bake time) but the identity strings are still emitted, so registry
  resolution still works.

  How to use it (recommended resolution order):

      asset = assetTable[index]
      domain   = strings[asset.domainId]
      registry = strings[asset.registryId]
      tex = engine.registry.tryResolve(domain, registry)   // preferred
      if tex == null and asset.dataLen > 0:
          tex = engine.decodeTexture(asset.bytes)            // fallback
      // cache tex keyed by asset index so shared refs decode once

  Assets are de-duplicated by (domain, registryValue, source) at bake time, so
  two components pointing at the same image share one record and one decode.
  The editor-side relative path is intentionally absent - do not look for it.


--------------------------------------------------------------------------------
  6. Element tree  (at treeOffset)
--------------------------------------------------------------------------------

  Exactly one root Element, encoded pre-order (a node, then all its children).
  An Element is:

  Size    Type      Description
  ------  ------    ----------------------------------------------------------
  4       u32       Element name string id
  16      u8[16]    Element UUID, raw RFC-4122 byte order
  2       u16       Component count
  ...               Component records (Component count of them)
  4       u32       Child count
  ...               Child Elements (Child count of them, recursive)

  What it's for: the UI hierarchy. The UUID is stable across bakes so an
  engine can keep references/bindings to a specific element.

  How to use it: decode recursively. Read the name and UUID, decode
  [componentCount] components onto the node, then decode [childCount] child
  Elements as children of this node. There is exactly one root; do not loop
  for siblings at the top level.


--------------------------------------------------------------------------------
  7. Component record
--------------------------------------------------------------------------------

  Size       Type    Description
  ------     ------  -----------------------------------------------------------
  4          u32     Component type-name string id (e.g. "Image", "Transform")
  4          u32     Payload length in bytes  [payloadLen]
  payloadLen bytes   Payload (the items below)

  Payload:
  2          u16     Field count
  ...                Fields (Field count of them)

  What it's for: payloadLen is a skip handle. It counts every byte after
  itself (the field count plus all fields). A loader that does not recognise
  the component type, or wants to ignore it, jumps payloadLen bytes and keeps
  going - the format stays forward-compatible as new component types appear.

  How to use it:

      typeName  = strings[typeNameId]
      payloadEnd = cursor_after_payloadLen + payloadLen
      comp = engine.createComponent(typeName)   // may be null if unknown
      read u16 fieldCount
      for each field: decode it; if comp != null, apply it (section 8)
      seek(payloadEnd)   // ALWAYS, even on success - this re-syncs the stream

  Always resync to payloadEnd after the fields. That single rule means one
  malformed or unknown component cannot derail the rest of the tree.


--------------------------------------------------------------------------------
  8. Field
--------------------------------------------------------------------------------

  Size    Type    Description
  ------  ------  --------------------------------------------------------------
  4       u32     Property-name string id
  1       u8      Type tag (below)
  varies          Value, layout determined entirely by the tag

  Tag  Name        Value encoding
  ---  ----------  ---------------------------------------------------------
  0    NONE        (no bytes)            unrepresentable / null
  1    BOOL        u8 (0 or 1)
  2    INT32       i32, little-endian
  3    INT64       i64, little-endian
  4    DOUBLE      f64, little-endian IEEE-754
  5    STRING      u32 string id
  6    COLOR       u32 packed 0xAARRGGBB
  7    ASSET_REF   u32 asset index (0xFFFFFFFF = no asset)
  8    POINT       f64 x, f64 y (two little-endian IEEE-754 doubles)

  What it's for: a self-describing key/value. The tag tells you exactly how
  many bytes follow, so you can decode (or skip) a field without knowing the
  component. Unknown tags are the one exception - their width is unknown, so
  if you hit one, abandon the component and resync via payloadEnd (section 7).

  How to apply fields to a component instance:

    * Most fields: set the property named strings[nameId] to the decoded
      value. INT32 also carries enum/flags values; COLOR is ARGB.

    * ASSET_REF: this field's NAME is an authoring path property
      (imagePath/fontPath/iconPath) but it carries an asset INDEX, not a path.
      Do NOT try to set a path. Instead:
          if index != 0xFFFFFFFF:
              asset = assetTable[index]
              comp.assetDomain        = strings[asset.domainId]
              comp.assetRegistryValue = strings[asset.registryId]
              comp.texture/font       = resolve(asset)   // section 5
      The component's visual content comes entirely from the resolved asset;
      the original editor path is not recoverable and is not needed.

    * POINT: a 2D vector (x, y). Used for Transform.position and
      Transform.scale (scale carries width/height in pixels, not a factor).
      Apply as the named property's two components.

  How the writer chose the tag (for reference): a property whose name ends in
  "Path" becomes ASSET_REF; "assetDomain"/"assetRegistryValue" are NOT emitted
  as fields (they are folded into the asset record and reapplied as above);
  everything else maps by type - bool->BOOL, integral->INT32/INT64,
  floating-point->DOUBLE, enum/flags->INT32, QColor->COLOR, point->POINT,
  string->STRING, anything else stringifiable->STRING, otherwise NONE.

  Note on flags: enum AND bit-flag properties both emit as INT32. A flags
  field carries the raw bitmask integer (not a list of set bits); decode it
  by testing bits.


--------------------------------------------------------------------------------
  8a. Transform component fields  (always present on every element)
--------------------------------------------------------------------------------

  Every Element has exactly one "Transform" component. It is the element's
  geometry and is emitted with these fields (names are the property-name
  string ids; order is not guaranteed - dispatch on the name):

  Field name       Tag     Meaning
  ---------------  ------  --------------------------------------------------
  position         POINT   (x, y) offset, in pixels, relative to the parent
  scale            POINT   (width, height) BASE size in pixels - NOT a factor
  rotationDegrees  DOUBLE  rotation about the element center, degrees
  anchors          INT32   anchor bitmask (see "Anchor / Stretch flags")
  stretch          INT32   stretch bitmask (LEFT|RIGHT = fill width, etc.)

  All five are always written. position and scale are single POINT fields
  (two f64s each) - there are no separate x / y / scaleX / scaleY scalar
  fields in v3. anchors and stretch are plain INT32 bitmasks; a value of 0
  means "no flags" (stretch defaults to 0; anchors defaults to 5 = LEFT|TOP).
  See section 8b for the flag values and how scale/anchors resolve.


--------------------------------------------------------------------------------
  8b. Anchor / Stretch flags & the sizing model
--------------------------------------------------------------------------------

  anchors and stretch (and Text.alignment) are bitmasks over these flags:

      NONE     = 0x00
      LEFT     = 0x01
      RIGHT    = 0x02
      TOP      = 0x04
      BOTTOM   = 0x08
      CENTER_X = 0x10
      CENTER_Y = 0x20

  stretch: LEFT|RIGHT (0x03) = fill parent width, TOP|BOTTOM (0x0C) = fill
  parent height.

  Effective size. scale is only the element's BASE size. The FINAL rendered
  size is resolved by applying the element's components in order; a content
  or layout component MAY overwrite it:
    - Visual components (Text, Image, Button, Icon, Sprite, Toggle, Tooltip,
      Dropdown, TextInput, ListRepeater, RadialMenu, DragSlot) size to their
      own intrinsic content and ignore scale.
    - StackLayout / GridLayout size to fit their children plus padding and
      ignore scale.
    - ScrollBox keeps scale only on its scroll axis; the cross axis fits
      children.
    - Slot is sized to its parent's rect.
    - Plain elements (Transform + Panel, or Transform alone) use scale
      directly.

  Positioning, using the FINAL size (W, H) within the parent rect:
      LEFT      localX = x
      RIGHT     localX = parentW - W - x
      CENTER_X  localX = (parentW - W)/2 + x
      TOP       localY = y
      BOTTOM    localY = parentH - H - y
      CENTER_Y  localY = (parentH - H)/2 + y
  final pos = parentTopLeft + (localX, localY); then rotate rotationDegrees
  about the FINAL rect's center. Anchoring/rotation ALWAYS use the final
  size, never raw scale.

  If the element's parent owns a layout component (StackLayout, GridLayout,
  ScrollBox), the parent positions this element: its own position / anchors
  / stretch are ignored for placement (scale still feeds the base size the
  layout measures). Do not also apply this element's anchors, or it will be
  double-positioned.


--------------------------------------------------------------------------------
  9. Reader requirements (conformance checklist)
--------------------------------------------------------------------------------

  * Reject the file unless the first 4 bytes are "UIB4" and the version u16
    equals 4. Do not attempt a "best effort" parse of a mismatched file.
  * Validate the magic + version BEFORE demasking. The header bytes (0..31)
    are NOT masked; everything from offset 32 onwards IS.
  * Apply the section 2a XOR mask over [32..fileSize) exactly once before
    reading the string table, asset table, or tree. The mask is its own
    inverse, so a second pass would re-mask the data.
  * Treat header section offsets as authoritative; never infer them from
    adjacency.
  * Bounds-check every read against the section/file size. A length or offset
    that runs past EOF invalidates the whole parse.
  * Read the string table fully before the asset table or tree.
  * Unknown component types and unknown field tags are non-fatal: skip via
    payloadLen / resync to payload-end and continue.
  * Cache resolved assets by asset index; multiple components legitimately
    share one index.

A reference decoder that round-trips this format back into an element tree
ships with UIMaker2 as UiBinReader (see src/scene/UiBinReader.*); the matching
encoder is UiBinWriter.
