================================================================================
  .uibin Binary UI Scene Format
  Specification Version 4
================================================================================

  Status:        Stable. Version 4 is the current wire format.
  Produced by:   UIMaker2, "Bake (.uibin)" command.
  Encoder:       src/scene/UiBinWriter.cpp
  Reference
  decoder:       src/scene/UiBinReader.cpp
  Primitives:    src/scene/UiBinCommon.{hpp,cpp}

  A .uibin file is a self-contained, binary-packed UI scene. It bundles a UI
  element hierarchy together with every referenced texture and font asset into
  one file that a game engine loads at runtime with zero external file
  dependencies.


--------------------------------------------------------------------------------
  0. Conventions
--------------------------------------------------------------------------------

0.1  Normative keywords

  The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT,
  RECOMMENDED, MAY and OPTIONAL in this document are to be interpreted as
  described in RFC 2119.

  Requirements are addressed to one of two roles, and each requirement names
  its role:

    PRODUCER   an implementation that writes a .uibin file.
    CONSUMER   an implementation that reads one.

  A requirement addressed to one role places no obligation on the other. Where
  the two differ deliberately - the flags word in 3.2 is the clearest example -
  this document says so explicitly.

0.2  Normative and informative text

  Sections 3 through 17 are NORMATIVE, except where a subsection is marked
  otherwise. Sections 0 through 2, every passage marked "Rationale", and both
  appendices are INFORMATIVE: they explain intent and MUST NOT be read as
  imposing requirements.

0.3  Notation

  u8, u16, u32, u64   unsigned little-endian integers of 8, 16, 32, 64 bits
  i32, i64            two's-complement little-endian signed integers
  f64                 IEEE-754 binary64, little-endian
  bytes[n]            n raw bytes, no framing and no terminator

  All multi-byte scalars are LITTLE-ENDIAN. There is no padding and no
  alignment requirement between fields; every structure is packed.

  Offsets are absolute byte positions from the start of the file.

0.4  Units

  Coordinates and extents are expressed in SCENE UNITS, a producer-defined
  abstract unit. The design canvas is 1920 x 1080 scene units. Scene units are
  not pixels; see section 13 for the relationship between scene units, virtual
  pixels and texels.


--------------------------------------------------------------------------------
  1. Design goals (informative)
--------------------------------------------------------------------------------

  * Opaque and fixed-layout. The format is deliberately not text-shaped. Every
    value is located by an explicit offset or a length prefix, never by
    scanning for a delimiter, so loading is a sequence of direct reads rather
    than a parse.

  * Little-endian everywhere, matching the target platforms, so reading a
    scalar is a direct load with no byte swapping.

  * Strings interned once. Every repeated string - component type names,
    property names, element names, asset identity - is stored a single time in
    a string table and referenced by a 4-byte id. The element tree contains no
    text.

  * Engine-facing asset identity is first class. Each asset carries an abstract
    (domain, registryValue) pair the engine resolves through its own registry,
    AND the raw baked bytes as a fallback. The producer's authoring path is
    deliberately absent: it is a tooling concept with no runtime meaning.

  * Forward-skippable. Component records are length-prefixed so a consumer can
    walk past a component type or field tag it does not understand rather than
    failing the whole file.

  * Eyeball-opaque body. Everything after the 32-byte header is run through a
    deterministic XOR stream (section 4) so a hex dump shows noise: no type
    names, no PNG or TTF magic, no element names. This is COSMETIC
    OBFUSCATION, NOT ENCRYPTION. Anyone holding this document can decode the
    file. It exists only to keep baked content from being casually readable.


--------------------------------------------------------------------------------
  2. File structure (informative overview)
--------------------------------------------------------------------------------

      +--------------------------------------------------+  offset 0
      |  Header, 32 bytes, NEVER obfuscated               |
      +--------------------------------------------------+  offset 32
      |  String table      (stringCount entries)          |  \
      +--------------------------------------------------+   |
      |  Asset table       (assetCount entries)           |   > obfuscated
      +--------------------------------------------------+   |
      |  Element tree      (exactly one root element)     |  /
      +--------------------------------------------------+  offset fileSize

  The three sections appear in this order and are contiguous. Their start
  offsets are carried in the header so a consumer never has to infer them.


--------------------------------------------------------------------------------
  3. Header
--------------------------------------------------------------------------------

3.1  Layout

  The header occupies the first 32 bytes and is NEVER obfuscated.

  Offset  Size  Type      Field               Value
  ------  ----  --------  ------------------  ----------------------------------
  0       4     bytes[4]  magic               ASCII "UIB4" (0x55 0x49 0x42 0x34)
  4       2     u16       version             4
  6       2     u16       flags               reserved; see 3.2
  8       4     u32       stringTableOffset   always 32
  12      4     u32       stringCount         number of string entries
  16      4     u32       assetTableOffset    first byte after the string table
  20      4     u32       assetCount          number of asset records
  24      4     u32       treeOffset          first byte after the asset table
  28      4     u32       fileSize            total file size in bytes

  The header carries THREE section offsets, TWO counts and one total size.

3.2  Requirements

  R3.1  PRODUCER MUST write magic exactly "UIB4" and version exactly 4.
  R3.2  PRODUCER MUST write flags as 0. All bits are reserved.
  R3.3  CONSUMER MUST reject a file whose magic is not "UIB4".
  R3.4  CONSUMER MUST reject a file whose version is not 4.
  R3.5  CONSUMER MUST verify magic and version BEFORE demasking the body, so a
        foreign or future file is rejected without the cost of a full pass.
  R3.6  CONSUMER MUST IGNORE every bit of the flags word. A non-zero flags
        value MUST NOT invalidate the parse.

        Rationale: R3.2 and R3.6 are deliberately asymmetric. Reserving the
        field while requiring consumers to ignore it is what allows a future
        version to use those bits without every existing consumer rejecting
        the file outright.

  R3.7  CONSUMER MUST reject a file whose fileSize does not equal the actual
        byte length of the file. This catches truncation cheaply.
  R3.8  CONSUMER SHOULD reject a header whose section offsets are not
        monotonically increasing, or where stringTableOffset != 32.


--------------------------------------------------------------------------------
  4. Obfuscation stream
--------------------------------------------------------------------------------

4.1  Algorithm

  Every byte from offset 32 to fileSize-1 inclusive is XORed with a keystream
  produced by a linear congruential generator seeded with a fixed constant:

      s = 0x5BC8A93D
      for i in 0 .. n-1:
          s    = (s * 1103515245 + 12345) mod 2^32
          k    = (s >> 16) and 0xFF
          b[i] = b[i] XOR k

  The transform is its own inverse: applying it twice restores the original
  bytes. The keystream depends only on the byte's index within the body, not
  on its content.

4.2  Requirements

  R4.1  PRODUCER MUST apply the stream to the whole body as ONE contiguous run
        beginning at offset 32. The three sections are not masked separately.
  R4.2  CONSUMER MUST demask the same single run before interpreting any body
        byte.
  R4.3  Implementations MUST NOT treat this as a security boundary.


--------------------------------------------------------------------------------
  5. String table
--------------------------------------------------------------------------------

5.1  Layout

  stringCount consecutive entries, beginning at stringTableOffset:

      Size    Type      Field
      ------  --------  ----------------------------------------------------
      4       u32       byteLength
      varies  bytes[n]  UTF-8 bytes, NOT null-terminated

5.2  Requirements

  R5.1  PRODUCER MUST emit string id 0 as the empty string.
  R5.2  A string id is an index into this table. CONSUMER MUST treat an id
        greater than or equal to stringCount as the empty string, and MUST NOT
        fail the parse because of one.
  R5.3  CONSUMER MUST bound every string read to the string table's extent
        (see R17.1).


--------------------------------------------------------------------------------
  6. Asset table
--------------------------------------------------------------------------------

6.1  Layout

  assetCount consecutive records, beginning at assetTableOffset:

      Size    Type      Field
      ------  --------  ----------------------------------------------------
      4       u32       domainId       string id, engine-facing domain
      4       u32       registryId     string id, engine-facing registry key
      4       u32       dataLen        length of the embedded payload
      varies  bytes[n]  data           raw file bytes, exactly as on disk

  The payload is the source file verbatim - PNG, TTF, OTF - with no added
  header, framing or compression.

6.2  Resolution order

  R6.1  CONSUMER MUST resolve an asset in this order and use the first source
        that yields a usable resource:
          1. If domainId and registryId both denote non-empty strings, resolve
             (domain, registryValue) through the engine's own asset registry.
          2. Otherwise, or if the registry yields nothing, and dataLen > 0,
             decode the embedded bytes.
          3. Otherwise, substitute a placeholder. CONSUMER MUST NOT fail the
             load because a single asset is unresolvable.

6.3  Requirements

  R6.2  Both id slots are ALWAYS written, but either MAY be string id 0 (the
        empty string) when the author set no engine identity. CONSUMER MUST
        treat an empty domain or registryValue as "no registry identity" and
        proceed directly to the embedded bytes.
  R6.3  dataLen MAY be 0, meaning the source file was missing at bake time.
  R6.4  CONSUMER SHOULD cache a decoded asset keyed by its INDEX, so several
        components referencing one asset share a single decode.


--------------------------------------------------------------------------------
  7. Element tree
--------------------------------------------------------------------------------

7.1  Layout

  Exactly one root element begins at treeOffset. An element record is:

      Size    Type       Field
      ------  ---------  ---------------------------------------------------
      4       u32        nameId          string id of the element's name
      16      bytes[16]  uuid            RFC 4122 binary form, big-endian
                                         fields as produced by toRfc4122()
      2       u16        componentCount
      varies             components      componentCount component records
      4       u32        childCount
      varies             children        childCount element records

  Children are emitted depth-first in authoring order.

7.2  Requirements

  R7.1  The uuid is stable across bakes of an unchanged scene and MAY be used
        as a persistent key.
  R7.2  The all-zero uuid is RESERVED and means "no stable identity". CONSUMER
        MUST NOT treat two all-zero uuids as the same element.
  R7.3  CONSUMER MUST impose a maximum nesting depth and reject a file that
        exceeds it. The reference decoder uses 64, counting the root as depth
        0.

        Rationale: a child record costs 26 bytes, so an unbounded recursive
        decoder can be made to exhaust its stack from a small file.


--------------------------------------------------------------------------------
  8. Component record
--------------------------------------------------------------------------------

8.1  Layout

      Size    Type    Field
      ------  ------  ------------------------------------------------------
      4       u32     typeId        string id of the component's type name
      4       u32     payloadLen    bytes following THIS field
      2       u16     fieldCount
      varies          fields        fieldCount field records (section 9)

  payloadLen counts every byte after payloadLen itself, including fieldCount.
  The record therefore ends at (offset of fieldCount) + payloadLen.

8.2  Requirements

  R8.1  CONSUMER MUST use payloadLen to skip a component whose type name it
        does not recognise, and MUST continue with the next component.
  R8.2  CONSUMER MUST seek to the record's declared end after reading a
        component, whether or not every field was consumed. This resynchronises
        after an unknown field tag.
  R8.3  CONSUMER MUST NOT read past the record's declared end while decoding
        its fields.
  R8.4  A component type name is an arbitrary string; section 12 lists the
        names this version's producer emits.


--------------------------------------------------------------------------------
  9. Field record and type tags
--------------------------------------------------------------------------------

9.1  Layout

      Size    Type    Field
      ------  ------  ------------------------------------------------------
      4       u32     nameId        string id of the property name
      1       u8      tag           see 9.2
      varies          value         layout determined entirely by the tag

9.2  Type tags

  Tag  Name       Value encoding                          Width
  ---  ---------  --------------------------------------  ----------
  0    NONE       (no bytes)                               0
  1    BOOL       u8, 0 or 1                               1
  2    INT32      i32                                      4
  3    INT64      i64                                      8
  4    DOUBLE     f64                                      8
  5    STRING     u32 string id                            4
  6    COLOR      u32, 0xAARRGGBB                          4
  7    ASSET_REF  u32 asset index, 0xFFFFFFFF = no asset   4
  8    POINT      f64 x then f64 y                         16

9.3  Requirements

  R9.1  CONSUMER MUST dispatch on the field NAME, not on position. Field order
        within a component is deterministic for a given producer version but is
        NOT part of this specification.
  R9.2  On encountering an unknown tag, CONSUMER MUST abandon the remainder of
        the component and resynchronise per R8.2. The width of an unknown tag
        cannot be inferred.
  R9.3  COLOR channels are STRAIGHT (not premultiplied), alpha in the high
        byte. A consumer compositing in premultiplied space MUST multiply the
        colour channels by alpha/255 itself. There is no gamma marker; treat
        values as sRGB.
  R9.4  INT32 carries enum and bit-flag values. A flag field carries the raw
        bitmask, not a list of set bits.
  R9.5  ASSET_REF carries an asset INDEX even though the property name ends in
        "Path". CONSUMER MUST NOT attempt to interpret it as a path. When the
        index is neither 0xFFFFFFFF nor out of range, CONSUMER MUST apply:
            component.assetDomain        = strings[assets[i].domainId]
            component.assetRegistryValue = strings[assets[i].registryId]
        and resolve the resource per section 6.
  R9.6  CONSUMER MUST treat an out-of-range asset index as "no asset" and MUST
        NOT fail the parse because of one.


--------------------------------------------------------------------------------
  10. Encoder algorithm (normative)
--------------------------------------------------------------------------------

  This section defines exactly which properties become fields and with which
  tag. A conforming producer MUST follow it so that consumers can rely on the
  catalogue in section 12.

10.1  Property scope

  R10.1  Only properties declared on the component's MOST-DERIVED class are
         emitted. Properties inherited from a base class are NOT emitted.

         Rationale: this is why no component carries an "objectName" field. It
         also means a property added to a shared base class would silently
         vanish from every baked file.

10.2  Per-property algorithm

  For each property in declaration order:

    1. If the property name is exactly "assetDomain" or "assetRegistryValue",
       SKIP it. These are not fields; they are folded into the asset record
       (section 6) and reapplied by the consumer per R9.5.

    2. If the property name ends with the exact-case ASCII suffix "Path",
       emit ASSET_REF. The value is the index of the asset record registered
       for that path, or 0xFFFFFFFF when the path and both identity strings
       are all empty.

    3. Otherwise, if the value's type is an enumeration or a flag set, emit
       INT32 carrying the raw integer.

    4. Otherwise, dispatch on the value's type:
           bool            -> BOOL
           32-bit integer  -> INT32
           64-bit integer  -> INT64
           floating point  -> DOUBLE
           colour          -> COLOR
           2D point        -> POINT
           string          -> STRING

    5. Otherwise, if the value can be converted to a string, emit STRING.

    6. Otherwise, emit NONE.

  R10.2  The "Path" suffix test is CASE-SENSITIVE. A property named "iconpath"
         is NOT an asset reference and is emitted as a STRING.

10.3  Asset identity is per slot

  A component MAY have more than one asset reference - Button has fontPath and
  imagePath - and each needs its own engine identity.

  R10.3  For an asset property named "<stem>Path", the identity is taken from
         the properties "<stem>Domain" and "<stem>RegistryValue" when those
         exist, and otherwise from the component-wide "assetDomain" and
         "assetRegistryValue".

         Button therefore carries fontDomain / fontRegistryValue for its font
         and the component-wide pair for its skin.

  R10.4  PRODUCER MUST NOT emit any property whose name ends in "Domain" or
         "RegistryValue" as a field. They are folded into the asset record.

  R10.5  CONSUMER applying R9.5 MUST write the identity back to the per-slot
         properties when they exist, and to the component-wide pair otherwise.


--------------------------------------------------------------------------------
  11. Geometry model
--------------------------------------------------------------------------------

11.1  The Transform component

  Every element carries exactly one component of type "Transform".

  Field            Tag     Default         Meaning
  ---------------  ------  --------------  ----------------------------------
  position         POINT   (0, 0)          offset from the anchored origin
  rotationDegrees  DOUBLE  0.0             rotation about the final centre
  scale            POINT   (100, 100)      BASE size, NOT a multiplier
  anchors          INT32   5 (LEFT|TOP)    placement bitmask
  stretch          INT32   0 (NONE)        stretch bitmask

  R11.1  PRODUCER MUST emit a Transform component for every element.
  R11.2  CONSUMER encountering an element with no Transform MUST substitute
         the defaults above.

11.2  Anchor and stretch flags

      NONE     = 0x00
      LEFT     = 0x01
      RIGHT    = 0x02
      TOP      = 0x04
      BOTTOM   = 0x08
      CENTER_X = 0x10
      CENTER_Y = 0x20

  R11.3  Within an axis the flags are mutually exclusive, and a conforming
         producer never sets more than one per axis. A consumer MUST
         nevertheless resolve a malformed combination deterministically, by
         this precedence:

             horizontal:  RIGHT  >  CENTER_X  >  LEFT     (LEFT is the default)
             vertical:    BOTTOM >  CENTER_Y  >  TOP      (TOP is the default)

11.3  Size resolution

  The final rendered size (W, H) is resolved in this order. This is the single
  most important clause for a consumer to implement correctly.

    1. Start from scale: W = scale.x, H = scale.y.

    2. For each axis INDEPENDENTLY, if that axis of scale is <= 0, the axis
       instead takes the intrinsic size contributed by the element's content
       component, if it has one (section 12 names the contributors). A
       non-positive scale axis is the ONLY way to request intrinsic sizing.

    3. If stretch has BOTH horizontal bits set (LEFT|RIGHT, 0x03):
           W = parentW - 2 * position.x
       If stretch has BOTH vertical bits set (TOP|BOTTOM, 0x0C):
           H = parentH - 2 * position.y
       position acts as a symmetric inset on a stretched axis. A single
       stretch bit on an axis has NO effect.

    4. If the element carries a layout component (StackLayout, GridLayout,
       ScrollBox) the layout determines the element's own size by fitting its
       children; see section 15.

    5. If the element carries a Slot component, its size is determined by its
       master; see section 16.

    6. Clamp both axes to a minimum of 0.0001.

  R11.4  scale is a SIZE in scene units. It is NOT a scale factor. A consumer
         that multiplies by it will be wrong by orders of magnitude.

11.4  Position resolution

  Using the FINAL size (W, H) from 11.3 within the parent's rect:

      LEFT      localX = position.x
      RIGHT     localX = parentW - W - position.x
      CENTER_X  localX = (parentW - W) / 2 + position.x
      TOP       localY = position.y
      BOTTOM    localY = parentH - H - position.y
      CENTER_Y  localY = (parentH - H) / 2 + position.y

  Final position = parentTopLeft + (localX, localY). Rotation is then applied
  about the centre of the final rect.

  R11.5  Anchoring and rotation MUST use the final size, never raw scale.
  R11.6  If the element's PARENT carries a layout component, the parent
         positions this element. CONSUMER MUST then ignore this element's
         position, anchors and stretch for placement, or it will be
         double-positioned. scale still feeds the base size the layout
         measures.

    sliceBottom      INT32      0

  ListRepeater
    itemCount        INT32      5
    itemHeight       INT32      40           extent along the RUN axis
    spacing          DOUBLE     2.0
    direction        INT32      0            0 = Vertical, 1 = Horizontal
    labels           STRING     "Item 1,..."  comma-separated, empties KEPT
    itemColor        COLOR      0xFF2D2D34
    alternateColor   COLOR      0xFF32323A
    borderColor      COLOR      0xFF464650

    itemHeight is the extent along whichever axis the list runs, so in
    Horizontal mode it is the item WIDTH. itemCount and labels are independent:
    surplus labels are ignored, missing ones are synthesised.

  Slot
    slotIndex        INT32      0
    masterKind       STRING     "TabContainer" or "RadialMenu"

  StackLayout
    direction        INT32      0            0 = Vertical, 1 = Horizontal
    spacing          DOUBLE     8.0
    padding          DOUBLE     8.0

  GridLayout
    columns          INT32      2
    spacingH         DOUBLE     8.0
    spacingV         DOUBLE     8.0
    padding          DOUBLE     8.0

  ScrollBox
    direction        INT32      0            0 = Vertical, 1 = Horizontal
    spacing          DOUBLE     8.0
    padding          DOUBLE     8.0


--------------------------------------------------------------------------------
  12.3  The Document component

  A component of type "Document" MAY appear on the ROOT element. It carries
  document-level settings that are not properties of any one element.

    renderModel   INT32    0    0 = Continuous, 1 = PixelGrid
    pixelUnit     DOUBLE   1.0  scene units per virtual pixel

  R12.1  PRODUCER MUST emit a Document component on the root whenever the
         document uses a rendering model other than the default.
  R12.2  CONSUMER MUST treat an absent Document component as
         renderModel = 0, pixelUnit = 1.0.
  R12.3  CONSUMER MUST treat a pixelUnit <= 0 as 1.0.

  Rationale: the .uibin header is a fixed 32 bytes and extending it would
  force a version bump that every existing consumer would reject. A component
  rides the machinery that is already there and is skipped harmlessly by a
  consumer that does not know it.


--------------------------------------------------------------------------------
  13. Pixel-perfect rendering model
--------------------------------------------------------------------------------

  Five component types carry a texture: Image, Button, Icon, Sprite and
  DragSlot. Each exposes four fields that control how that texture fills its
  element's rect.

13.1  Fields

  textureFill   INT32   0 = STRETCH, 1 = WRAP
  cropAnchor    INT32   0..8, reading order, see 13.2
  cropOffsetX   INT32   signed texel shift of the horizontal tiling phase
  cropOffsetY   INT32   signed texel shift of the vertical tiling phase

  R13.1  CONSUMER MUST treat a textureFill value other than 0 or 1 as 0, and a
         cropAnchor outside 0..8 as 4 (Center). cropOffsetX and cropOffsetY are
         NOT clamped by the producer and MAY be any i32.

13.2  Crop anchor values

      0 TopLeft     1 Top      2 TopRight
      3 Left        4 Center   5 Right
      6 BottomLeft  7 Bottom   8 BottomRight

  The anchor resolves independently per axis:

      horizontal:  0,3,6 -> NEAR    1,4,7 -> CENTER    2,5,8 -> FAR
      vertical:    0,1,2 -> NEAR    3,4,5 -> CENTER    6,7,8 -> FAR

13.3  STRETCH (textureFill = 0)

  The texture is scaled to the destination rect. This is the traditional
  behaviour and imposes no relationship between texels and pixels.

13.4  WRAP (textureFill = 1)

  One texel occupies exactly one VIRTUAL PIXEL. The texture is never scaled.
  A destination larger than the texture REPEATS it; a destination smaller
  CROPS it. A 9-slice pins the edges so only the interior repeats.

  A virtual pixel is a square of `unit` scene units. See 13.6 for how a
  consumer obtains `unit`.

13.5  Per-axis span algorithm (normative)

  Solve each axis independently; the 2D result is their cross product. That is
  precisely why corners never repeat, edges repeat along one axis only, and
  the interior repeats along both.

  Inputs, all in texels except d:
      n     source extent
      a, b  near and far 9-slice insets, 0 for an unsliced axis
      d     destination extent in VIRTUAL PIXELS
      side  NEAR, CENTER or FAR, from the crop anchor
      off   signed crop offset

  Output: a list of spans (srcStart, dstStart, len). Every span copies texels
  1:1; there is no scale factor anywhere in the result.

      if n <= 0 or d <= 0: no spans

      # An inset pair with no interior cannot describe a slice on this axis.
      if a < 0 or b < 0 or a + b >= n:
          a = 0; b = 0

      # A destination narrower than the insets shrinks them rather than
      # dropping an edge entirely.
      da = min(a, d / 2)              # integer division
      db = min(b, d - da)

      if da > 0: emit (0,      0,      da)      # near band, never repeats
      if db > 0: emit (n - db, d - db, db)      # far band,  never repeats

      dstMid = d - da - db                      # interior, virtual pixels
      srcMid = n - a - b                        # interior period, texels
      if dstMid <= 0 or srcMid <= 0: done

      shortfall = (srcMid - (dstMid mod srcMid)) mod srcMid
      phase = 0
      if side == FAR:    phase = shortfall
      if side == CENTER: phase = shortfall / 2  # integer division
      phase = ((phase + off) mod srcMid + srcMid) mod srcMid

      x = -phase
      while x < dstMid:
          visibleStart = max(0, x)
          visibleEnd   = min(dstMid, x + srcMid)
          len          = visibleEnd - visibleStart
          if len > 0:
              emit (a + (visibleStart - x), da + visibleStart, len)
          x = x + srcMid

  R13.2  CONSUMER implementing WRAP MUST reproduce this algorithm exactly.
         The spans MUST tile the destination with no gap and no overlap, and
         MUST never sample outside the texture.
  R13.3  CONSUMER MUST sample with nearest-neighbour filtering in WRAP mode,
         regardless of the pixelated field.

  Worked example. The reference asset is 200 x 20 texels with insets
  left 3, top 3, right 3, bottom 4, drawn into 400 x 40 virtual pixels with
  anchor Center:

      X: [0,3) [3,103) [103,297) [297,397) [397,400)
      Y: [0,3) [3,13)  [13,26)   [26,36)   [36,40)

  giving 25 draw calls. Destination columns 0..2 are texels 0..2 and columns
  397..399 are texels 197..199 - the border is 1:1 and does not warp.

13.6  The virtual pixel unit

  R13.4  The `unit` is Document.pixelUnit (section 12.3). A consumer MUST use
         1.0 when no Document component is present.

13.7  The 9-slice source

  For Button, the insets come from sliceLeft/sliceTop/sliceRight/sliceBottom.

  R13.5  Image, Icon, Sprite and DragSlot carry sliceLeft, sliceTop,
         sliceRight and sliceBottom exactly as Button does. All four default
         to 0, which means "unsliced".

  The producer populates them from an authoring-time sidecar XML when the image
  path is assigned. The sidecar is NOT embedded in the bake - the fields are
  what reaches the engine. For reference, it sits beside the image with the
  extension replaced by .xml:

      <sprite>
          <slice left="3" top="3" right="3" bottom="4"/>
      </sprite>

  Unknown elements inside <sprite> are ignored, so the schema can grow.


--------------------------------------------------------------------------------
  14. Text rendering
--------------------------------------------------------------------------------

  Two component types carry glyph runs: Text and Button. They share the font
  resolution rules and differ in which colour field names the glyph fill -
  Text.color versus Button.textColor.

14.1  Font resolution

  R14.1  CONSUMER MUST try these sources in order and use the first that
         yields a usable face:
           1. If fontPath references an asset, resolve its (domain,
              registryValue) through the engine's font registry. If the
              registry returns a face, USE IT - do not override it with
              fontFamily even if a system font of that family exists.
           2. Otherwise, if that asset's dataLen > 0, load the embedded bytes.
           3. Otherwise, look up fontFamily among installed fonts.
           4. Otherwise, use the engine's default UI font.
  R14.2  CONSUMER MUST NOT refuse to render because a font is missing. A
         missing font degrades to a default, never to nothing.
  R14.3  fontFamily is a HINT for steps 3 and 4 only. A producer-side family
         name carries no guarantee the consuming machine has it.

14.2  Pixel size

  pixelSize is the GLYPH CELL HEIGHT in pixels - equivalent to FreeType's
  FT_Set_Pixel_Sizes(face, 0, pixelSize). It is not a point size and not an em.

  R14.4  CONSUMER MUST set the face's pixel height to this value before
         measuring or rasterising, and MUST NOT scale a rasterised result to
         fake the size: kerning and hinting would be wrong.
  R14.5  pixelSize is written UNCLAMPED and MAY be 0 or negative. CONSUMER
         MUST clamp it to at least 1.

14.3  Alignment

  Text.alignment is the anchor bitmask from 11.2 applied to the glyph RUN
  inside the element's final rect. It is independent of Transform.anchors,
  which place the element itself.

  R14.6  CONSUMER MUST resolve alignment with the precedence in R11.3:
         horizontal RIGHT > CENTER_X > LEFT, vertical BOTTOM > CENTER_Y > TOP.

      LEFT      0x01   left edge of run at left edge of rect
      CENTER_X  0x10   run centred horizontally
      RIGHT     0x02   right edge of run at right edge of rect
      TOP       0x04   ascender top at top edge of rect
      CENTER_Y  0x20   run's visual centre at rect centre
      BOTTOM    0x08   descender bottom at bottom edge of rect

14.4  hasBackground

  R14.7  When Text.hasBackground is true, the reference renderer draws the
         glyph run a second time UNDERNEATH the real run, offset by
         max(1, pixelSize / 16) pixels on both axes, in rgba(0, 0, 0, 160).
         It is a translucent drop shadow, not an opaque backdrop. A consumer
         MAY substitute an equivalent legibility treatment.


--------------------------------------------------------------------------------
  15. Layout components
--------------------------------------------------------------------------------

  R15.1  An element carrying StackLayout, GridLayout or ScrollBox positions
         its CHILDREN and derives its OWN size from them. CONSUMER MUST re-run
         the layout at load; the positions stored in each child's Transform
         are authoring leftovers and MUST be ignored for placement (R11.6).

15.1  StackLayout

      offset = padding
      for each child in order:
          if direction == 0 (Vertical):   child at (padding, offset)
          else:                           child at (offset, padding)
          offset += child extent along the run axis + spacing
      remove the trailing spacing, add padding
      own size = (maxCrossExtent + 2*padding) across, offset along the run

  There is no cross-axis alignment and no fill: every child sits at `padding`
  on the cross axis.

15.2  ScrollBox

  Identical placement to StackLayout, with one difference: the element keeps
  its own scale on the SCROLL axis and fits children on the cross axis. The
  format carries no scroll offset and no content extent.

15.3  GridLayout

      pass 1: colWidth[i mod columns]  = max child width in that column
              rowHeight[i div columns] = max child height in that row
      pass 2: place each child at the cumulative sum of preceding columns and
              rows, plus spacingH / spacingV, offset by padding

  Cells are top-left packed; a child smaller than its cell leaves a gap.
  There is no span, no alignment and no uniform-cell mode.

  R15.2  Layout components measure each child's UNROTATED extent. A rotated
         child is measured by its axis-aligned local rect.


--------------------------------------------------------------------------------
  16. Slots and tab containers
--------------------------------------------------------------------------------

  A Slot is a container child materialised by a master component. Its
  masterKind names the master's type and its slotIndex identifies which slot
  it is.

  R16.1  When masterKind is "TabContainer": the slot's rect is the parent's
         rect inset from the top by the master's tabHeight, i.e.
         height = parentH - tabHeight, positioned tabHeight below the parent's
         top edge. The slot is VISIBLE only when its slotIndex equals the
         master's activeTab.
  R16.2  When masterKind is "RadialMenu": the slot fills the parent rect. The
         format does NOT describe per-slice placement; a consumer wanting
         radial placement MUST derive it from sliceCount and the radii.
  R16.3  Slot indices are not guaranteed contiguous or ordered; dispatch on
         slotIndex, not on child order.


--------------------------------------------------------------------------------
  17. Conformance
--------------------------------------------------------------------------------

17.1  Producer checklist

  [ ] magic "UIB4", version 4, flags 0                             R3.1, R3.2
  [ ] fileSize equals the real file length                          R3.7
  [ ] body obfuscated as one run from offset 32                     R4.1
  [ ] string id 0 is the empty string                               R5.1
  [ ] a Transform component on every element                        R11.1
  [ ] properties emitted per the section 10 algorithm               R10.1, R10.2
  [ ] the file is decoded back and validated before it replaces
      an existing file at the target path

17.2  Consumer checklist

  [ ] reject on magic mismatch                                      R3.3
  [ ] reject on version mismatch, BEFORE demasking                  R3.4, R3.5
  [ ] ignore the flags word entirely                                R3.6
  [ ] reject when fileSize disagrees with the real length           R3.7
  [ ] bound every read to its SECTION, not merely to the file       R17.1
  [ ] cap element nesting depth                                     R7.3
  [ ] skip unknown component types via payloadLen                   R8.1
  [ ] resynchronise to payloadEnd after an unknown field tag        R8.2, R9.2
  [ ] treat out-of-range string ids as empty                        R5.2
  [ ] treat out-of-range asset indices as absent                    R9.6
  [ ] never fail the load because one asset is unresolvable         R6.1
  [ ] clamp pixelSize to >= 1                                       R14.5
  [ ] resolve anchors and alignment with the stated precedence      R11.3
  [ ] re-run layouts and ignore stored child positions              R15.1
  [ ] use the FINAL size for anchoring and rotation                 R11.5

  R17.1  CONSUMER MUST bound reads to the SECTION being parsed, not merely to
         the file. A string-table length that overruns into the asset table
         must be rejected, not silently tolerated because it still lies inside
         the file.

17.3  Structural limits

  componentCount   u16    at most 65535 per element
  fieldCount       u16    at most 65535 per component
  childCount       u32    at most 4294967295 per element
  string length    u32    per entry
  asset dataLen    u32    per record
  nesting depth    -      at most 64 in the reference decoder (R7.3)
  total file size  u32    below 2 GiB in practice; see A.4

  R17.2  PRODUCER MUST NOT emit a scene that exceeds any of these.


--------------------------------------------------------------------------------
  Appendix A. Known gaps and defects (informative)
--------------------------------------------------------------------------------

  Recorded so implementers are not surprised. Each is a candidate for a
  version 5.

A.1  RESOLVED. The rendering model and the 9-slice insets are now in the file.

  Formerly the document-level rendering model lived only in the editor's
  scene.json and the 9-slice insets only in a sidecar XML, so a consumer could
  not reproduce WRAP rendering from a .uibin alone.

  Both are now carried: the rendering model as a "Document" component on the
  root element (section 12.3) and the insets as sliceLeft/sliceTop/sliceRight/
  sliceBottom fields on every textured component (section 13.7). No format
  version bump was needed - both ride the existing component machinery, so a
  consumer that does not recognise them skips them by payloadLen.

A.2  RESOLVED. ProgressBar.direction now matches every other direction field.

  It was the only component ordering the enum Horizontal = 0, while
  StackLayout, ScrollBox and ListRepeater all use Vertical = 0 - and the
  producer's property editor presents all four with a Vertical-first list, so
  a bar authored as "Vertical" was baked as Horizontal.

  ProgressBar.direction is now Vertical = 0, Horizontal = 1 like the others.
  scene.json carries a "sceneVersion" key and the producer migrates values
  written by an older build, so existing scenes keep their appearance. A
  .uibin is a build artifact and is simply rebaked.

A.3  RESOLVED. Asset identity is per slot.

  Button has both fontPath and imagePath, but a component used to carry a
  single (assetDomain, assetRegistryValue) pair, which the producer stamped
  onto BOTH asset records; a consumer applying R9.5 to each reference in turn
  kept whichever came last, so the font resolved through the skin's key.

  Identity is now per asset slot by the naming convention in 10.3. Button
  carries fontDomain / fontRegistryValue for fontPath and keeps assetDomain /
  assetRegistryValue for imagePath.

A.4  The container is int-bounded in practice

  Every length in the header is u32, but the reference decoder's cursor
  arithmetic is 32-bit signed, so files at or above 2 GiB cannot be read by it
  even though they are representable.

A.5  Round-trip validation is structural only

  The producer re-reads every file it writes and aborts the write on failure,
  so a malformed container never replaces a good one. That check proves
  FRAMING only: it never compares decoded values against the source scene, so
  a producer bug that writes well-framed but wrong values passes it.


--------------------------------------------------------------------------------
  Appendix B. Version history (informative)
--------------------------------------------------------------------------------

  v4  Current. Magic "UIB4". Adds the XOR-obfuscated body (section 4) over v3.
      Later v4 revisions added the POINT tag for Transform.position and
      Transform.scale - files written by an early v4 producer encoded those
      two through the stringify fallback and are NOT readable by a current
      decoder. Most recently, the four pixel-perfect fields of section 13 were
      added to Image, Button, Icon, Sprite and DragSlot; a decoder that does
      not know them skips them by name with no special handling.

  v3  Magic "UIB3". Introduced the engine-facing (domain, registryValue) asset
      identity. No obfuscation.
